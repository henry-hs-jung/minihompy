# 방문자 식별과 관리자 권한

## 결정

개인 미니홈피 하나만 제공한다. 방문자 회원가입·로그인 화면은 만들지 않는다. 닉네임은 브라우저에 기억하되 실명이나 동일인 보증으로 취급하지 않는다. 변경한 닉네임은 다음 글부터 적용하며, 과거 글의 이름은 작성 당시 값으로 저장할 예정이다.

방문자가 처음 작성할 때 Supabase 익명 인증을 사용한다. 내부적으로 `auth.users`에 익명 사용자 기록과 세션이 생긴다. 읽기만 할 때는 생성하지 않는다. 이메일·비밀번호를 받지 않는다. 동일 브라우저에 유효한 세션이 남아 있는 동안 본인 글을 관리한다. 브라우저 저장소 삭제, 시크릿 창 종료, 세션 만료/폐기로 접근을 잃을 수 있으며 닉네임으로 복구하지 않는다. 공유 브라우저에서는 같은 방문자로 인식된다.

[Supabase 익명 인증 공식 문서](https://supabase.com/docs/guides/auth/auth-anonymous)

## 권한 계약

| 구분 | 식별 | 허용 범위 |
| --- | --- | --- |
| 읽기 방문자 | 세션 없음 | 공개 콘텐츠 조회 |
| 작성 방문자 | 익명 인증 UID | 허용 폴더의 글·방명록·댓글 작성, 본인 글 수정·삭제 |
| 관리자 | 서버의 관리자 UUID 목록 | 개인 설정·폴더·본인 콘텐츠 관리, 다른 사람 글 삭제 |

타인 글의 내용 수정은 관리자에게도 허용하지 않는 방향으로 설계한다. 비공개 방명록 조회는 작성자와 관리자만 허용한다. 닉네임 중복은 허용하되 관리자 배지는 신뢰 가능한 관리자 식별 결과로만 표시한다. 작성자 UID와 표시 이름을 별도 필드로 저장한다.

DB 권한은 후속 콘텐츠 테이블의 RLS에서 검사한다. 익명 인증 사용자도 Postgres에서는 `authenticated` 역할이므로 이 역할 전체에 관리자 권한을 주면 안 된다. UI 판정은 편의를 위한 것이며 DB 권한 검사를 대체하지 않는다. 사용자 metadata나 localStorage의 값으로 관리자를 판정하지 않는다.

## 이번에 추가한 기반

- `visitor-identity.js`: Supabase SDK 클라이언트를 주입받는 식별 모듈. 닉네임 기억, 현재 사용자 확인, 첫 작성 시 익명 식별, 중복 호출 방지. 인증 오류 시 새 사용자로 자동 대체하지 않는다.
- `supabase/migrations/202609130001_identity.sql`: 브라우저가 수정할 수 없는 관리자 목록과 본인 관리자 여부를 반환하는 함수. 최초 관리자 등록은 신뢰할 수 있는 SQL 작업으로만 수행한다.
- `scripts/verify-identity.mjs`: SDK 모의 객체로 동작과 실패 경로 검사.

아직 SDK 연결·관리자 로그인 UI·CAPTCHA UI·실제 작성 폼·콘텐츠 RLS는 구현하지 않았다. 모듈을 로드해도 인스턴스를 만들지 않으므로 네트워크 요청과 화면 변화가 없다. 실제 DB에서 마이그레이션을 실행하거나 RLS 통합 테스트를 수행한 상태가 아니다.

## Supabase 설정 순서

1. 프로젝트 URL과 publishable key를 준비한다. secret/service_role 키는 브라우저·저장소에 넣지 않는다.
2. 관리자용 영구 사용자를 만들고 해당 UUID를 확보한다. 일반 방문자에게 회원가입 화면은 제공하지 않는다.
3. SQL Editor 또는 CLI로 마이그레이션을 적용한다. 신뢰 가능한 SQL에서 `insert into private.minihompy_admins (user_id) values ('관리자 UUID');`를 실행한다. 실제 UUID로 대체해야 한다.
4. Anonymous Sign-Ins와 CAPTCHA를 설정한다. 익명 가입과 영구 계정 가입 관련 설정의 영향을 프로젝트에서 확인한다. 관리자 로그인과 방문자 익명 세션은 SDK storageKey를 분리해 서로 덮어쓰지 않도록 연결한다.
5. 게시판 테이블·RLS를 추가하고 소유자 변경 차단, 타인 수정 차단, 공개/비공개 조회를 실제 DB에서 검증한다. CAPTCHA만으로 게시물 도배를 막을 수 없으므로 작성 빈도·길이 제한도 서버에서 적용한다.
6. 작성 폼에 닉네임 기억과 익명 세션을 연결한다. 첫 작성 전에 해당 브라우저에 작성 권한을 기억한다는 점과 저장소 삭제 시 복구 불가를 안내한다.

배포는 HTTPS GitHub Pages를 기준으로 한다. file:// 화면 검수와 실제 인증 환경을 구분한다. 커스텀 도메인으로 변경하면 브라우저 저장소의 출처가 달라지므로 방문자 식별을 그대로 유지한다고 약속하지 않는다. 운영 전 만료된 익명 계정 정리와 삭제 시 콘텐츠 보존 정책도 확정한다.
