# 사진첩 작성과 이미지

## 현재 동작

- 사진첩은 `photo_folders`, `photo_posts`를 조회한다. 과거 `photos-data.js` 샘플은 실행되지 않는다.
- 폴더는 기존처럼 1단계와 구분선만 허용한다. 초기 실제 폴더는 `일상` 하나다. 폴더 관리 UI는 아직 없다.
- 관리자만 사진 올리기/수정/삭제를 볼 수 있다. 수정은 해당 관리자 본인 글만 가능하다.
- 본문은 Quill 2.0.3으로 편집한다. 사진 파일 선택 직후 커서 위치에 로컬 Blob 미리보기를 넣는다. 사진 사이에 글을 입력할 수 있다.
- 파일 선택, 이미지 붙여넣기, 파일 드롭을 지원한다. 외부 HTML의 이미지는 붙여넣지 않는다. 이번 단계의 서식은 일반 텍스트와 사진뿐이다.
- 저장을 누르면 사용 중인 새 사진부터 업로드하고, 순서 있는 텍스트/이미지 블록을 JSONB에 기록한다. HTML은 저장하거나 실행하지 않는다.
- JPG/PNG/WEBP/GIF, 장당 최대 6MB, 글당 사진 1~20장, 제목 120자, 본문 50,000자/100블록 이내. 원본을 업로드하며 리사이즈하거나 EXIF를 제거하지 않는다.
- 읽기 화면은 2개 글씩 펼쳐보기와 페이지 이동을 유지한다. [공통 댓글](comments.md)의 작성·본인 수정·삭제를 지원한다.

## 저장과 실패

- 메뉴를 오가도 메모리 초안은 유지한다. 새로고침/탭 닫기에는 경고하지만 초안을 영구 저장하지는 않는다. 로그아웃하면 초안을 지운다.
- 업로드/DB 저장 실패 시 초안을 유지한다. 업로드 완료 파일은 재시도 시 재사용한다.
- 업로드 응답 유실 후 같은 경로가 이미 있으면 원격 파일과 로컬 파일의 바이트를 비교한다. 일치할 때만 재사용하며 덮어쓰지는 않는다.
- 글 UUID는 작성 시작 때 생성한다. 새 글 저장 응답이 유실되어 재시도해도 동일 ID와 내용이 확인되면 저장된 글을 반환한다.
- 수정/삭제는 revision 비교로 동시 변경 충돌을 막는다.
- 수정으로 빠진 사진과 삭제한 글의 사진은 글 저장/삭제가 성공한 뒤 Storage API로 정리한다. 게시 중인 이미지 경로는 Storage DELETE 정책으로 보호한다.
- 저장 시도 전 취소는 서버 파일을 만들지 않는다. 부분 업로드 후 취소는 확인된 업로드 파일을 정리한다. 통신 단절, 브라우저 종료, 로그아웃, 응답 유실은 미사용 파일을 남길 수 있다. 자동 배치 정리는 아직 없으며 Storage에서 `photo_posts.body`에 참조되지 않는 경로를 확인해 정리해야 한다. DB 행을 직접 지워 Storage 파일을 삭제하지 않는다.

## 공개 범위와 권한

`minihompy-photos`는 전체공개 사진 전용 public bucket이다. 파일 URL을 아는 사람은 로그인 없이 볼 수 있다. 저장 버튼 이후 업로드된 사진은 DB 글 저장 전에도 URL로 열릴 수 있다. 비공개 사진을 보관하는 용도로 사용하지 않는다.

파일 업로드/정리는 관리자 RLS로 제한하고, 파일 덮어쓰기는 허용하지 않는다. 폴더/글 DB도 관리자 정책과 열 단위 권한으로 보호한다. 공개 버킷은 읽기 공개와 업로드 권한이 별개다. [Supabase Storage 권한](https://supabase.com/docs/guides/storage/security/access-control), [공개 버킷](https://supabase.com/docs/guides/storage/buckets/fundamentals).

`202609130004_photos.sql`은 사용자가 실제 프로젝트에서 실행 성공을 확인했다. 실제 공개 폴더 조회도 확인했다. 원격 관리자 쓰기는 계정 소유자가 직접 검증한다.

## 검증

- `scripts/verify-photos-writing.mjs`: 실제 SDK/Quill + 모의 API, 데스크톱/모바일. 인라인 미리보기, 글/사진 순서, 조기 업로드 방지, 초안 유지, 저장/수정/삭제, 실패/재시도/충돌/로그아웃, 이미지 크기 검사.
- `scripts/verify-photos-db.mjs`: 로컬 PGlite와 최소 Storage 스키마로 마이그레이션, 관리자 권한, 블록 제약, revision, 게시 중 파일 삭제 보호를 검증한다. 실제 Storage 서버의 MIME/파일 크기 제한은 대체하지 않는다.
- 스크린샷: `docs/verification/photos-writing/`.
